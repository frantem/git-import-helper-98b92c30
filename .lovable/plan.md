План устранения багов времени доставки и самовывоза

Что я нашёл по текущему товару

- Товар `/product/5f6bfe98-7360-462a-b1ad-e033a2d17a09` имеет `prep_time_minutes = 840` и продавца с графиком 10:00–17:00, кроме понедельника.
- Поэтому за один рабочий день товар физически не успевает приготовиться: 840 минут = 14 часов, а рабочее окно продавца = 7 часов. Нормальная логика должна переносить готовку на следующий рабочий день.
- Сейчас самовывоз показывает “нет доступных дат”, а доставка показывает `29.04 18:00–19:00` из-за ошибок в переносе времени, округлении, timezone/date arithmetic и разной логики между “самовывозом” и “доставкой”.

Что будет исправлено

1. Единый источник времени Minsk
- Убрать локальные копии `getMinskTime()` из `Checkout.tsx`.
- Вынести в `pickupUtils.ts` экспортируемые функции для Minsk-даты и сравнения дат.
- Все проверки “сегодня/завтра/прошлая дата” будут использовать один и тот же Minsk day, а не локальный timezone браузера.

2. Абсолютные даты вместо “минут от полуночи”
- Переписать ядро расчёта на абсолютные timestamps/Date в Minsk-календаре.
- Исправить пересечение дня: если `ready + delivery` выходит за конец дня/рабочего окна доставки, остаток не должен форматироваться как `24:10` или давать кривой слот; нужно перейти на следующий доступный день доставки.
- Форматировать только валидные минуты `0..1440`, где `24:00` разрешён только как конец окна, но не как старт слота.

3. Исправить carryover
- Готовка будет распределяться по рабочим окнам продавца корректно:
  - остаток приготовления переносится через выходные/занятые/отпускные дни;
  - если товар готов ровно к закрытию, для самовывоза этот день недоступен, но сам товар считается уже готовым и может быть выдан в следующий доступный рабочий слот;
  - для доставки готовность товара и возможность доставки будут считаться отдельно.

4. Развести два понятия cutoff
- Текущий `cutoff_time_minutes` сейчас смешивает старое “время развоза” и новое “дедлайн принятия заказа”. Это даёт неправильную логику.
- Я приведу поведение к понятной модели без добавления новых настроек БД на этом этапе:
  - `delivery_start_hour` / `delivery_end_hour` = реальные рабочие часы доставки;
  - `avg_delivery_time_minutes` = время от готовности товара до прибытия;
  - `cutoff_time_minutes` = ограничение только для принятия/переноса доставки на сегодня, а не время, в которое всегда надо везти.
- Текст в админке нужно поправить, чтобы не вводил в заблуждение: сейчас там написано “Время развоза”, хотя новая логика использует доставку по окну.

5. Округление времени прибытия
- Округление будет применяться после расчёта `ready + avgDelivery`, вверх к ближайшим 30 минутам.
- Если после округления слот не помещается в рабочее окно доставки, выбирается следующий доступный день/окно.
- Слот должен иметь минимум 30 минут и не выходить за конец доставки.

6. Единая логика для всех режимов
- Убрать/заменить старую функцию `calculateDeliveryHours()` из `useDeliveryTime.ts`, потому что она считает по старой схеме `cutoff + prep` и расходится с `calculateDeliveryTime()`.
- Если функция ещё нужна для карточек/хуков, она будет делегировать в новое ядро или будет удалена, если не используется.
- “Ближайшая доставка”, “Доставка в указанное время”, “Самовывоз” и сохранённое `estimated_delivery_time` будут брать данные из одного расчётного ядра.

7. Валидация входных данных
- Добавить нормализацию:
  - `prep_time_minutes`: только число `>= 0`, `0` валиден;
  - график: `start < end`, время в диапазоне 00:00–24:00;
  - настройки доставки: start/end/cutoff/avgDelivery проверяются и получают безопасные fallback;
  - пустой/битый `pickup_slots` не должен давать случайную доставку “в любое время”.

8. Производительность
- Сейчас `getMinskTime()` вызывается в циклах и разных функциях много раз.
- Будет создан один `nowMinsk` в начале расчёта и передаваться вниз через options/context.
- Даты на 14 дней будут генерироваться один раз на расчёт, без повторного пересчёта текущего времени внутри каждой итерации.

9. UI в Checkout
- Если для самовывоза нет доступной даты, карточка должна явно объяснять причину: “Нет доступных дат по графику продавца/в ближайшие 14 дней”, а не просто показывать пустой календарь.
- Если ближайшая доставка невозможна, нельзя показывать “Привезем ваш заказ: ...” с кривым временем; нужно показывать “Нет доступных дат для доставки”.
- Кнопку “Заказать” нужно блокировать для courier fast, если `fastDeliveryResult` = “Нет доступных дат”.

10. Проверочные сценарии
После правок прогоню проверку на сценариях:
- `5f6bfe98-7360-462a-b1ad-e033a2d17a09`: 840 минут, продавец 10:00–17:00, перенос через несколько рабочих окон без `17:00–17:00` и без неправильной даты доставки.
- `263ae7ff-fbe1-45bd-a6da-e3566db16857`: тот же кейс с 840 минутами, минимум 30 минут на самовывоз.
- `d82788df-41cb-48d7-ab13-0c3556e093e5`: `prep_time_minutes = 0`, график вторник/пятница с 09:00, первый самовывоз с 09:00, не 10:30.
- Доставка не раньше `готовность всех продавцов + avg_delivery_time_minutes`.
- Даты в календаре доставки и самовывоза совпадают с текстом “Ближайшая доставка/самовывоз”.
