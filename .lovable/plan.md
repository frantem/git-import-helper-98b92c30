## Что нашёл

Лог сети показал реальную причину: PATCH `/profiles` вернул **409 / `idx_profiles_phone_unique`** — введённый телефон уже привязан к другому профилю (видимо, к вашему основному аккаунту/продавцу). Текущий `handleSaveProfile` показывает `toast.error("Ошибка сохранения")` без деталей, поэтому ошибка выглядит как «всё ок, но не сохранилось».

Плюс: сейчас на странице Settings телефон записывается в профиль **без OTP-проверки**, хотя для регистрации по телефону мы код требуем. Это надо унифицировать — если пользователь зашёл через Email и впервые вводит телефон, нужно подтвердить его кодом по SMS (тем же `send-otp` / `link-phone-to-account`, что уже есть).

## Что сделаю

### 1. `src/pages/Settings.tsx` — раздел «Личные данные»
- Хранить отдельно «исходный сохранённый телефон» (`savedPhone`) и текущее значение поля (`phone`).
- Поле телефона форматировать через `formatBYPhone` (как в `PhoneAuthForm`); валидация через `isValidBYPhone`.
- При нажатии **Сохранить**:
  - Если телефон не менялся → обычное обновление имени/адреса/аватара (без поля `phone`).
  - Если телефон изменился или впервые задаётся → не сохраняем профиль сразу, а открываем диалог OTP:
    1. Вызов `supabase.functions.invoke("send-otp", { body: { phone } })`.
    2. Модалка с 4-клеточным вводом кода (логика как в `PhoneAuthForm`: auto-focus, paste, countdown на повтор).
    3. На подтверждении вызов `supabase.functions.invoke("link-phone-to-account", { body: { phone, code } })` — он сам проверит код, проверит уникальность телефона и обновит `profiles.phone` + `phone_verified=true` через service role (минуя RLS и unique-конфликты на уровне клиента).
    4. После успеха — отдельным PATCH сохраняем `full_name`, `delivery_address`, `avatar_url`, `email` (без `phone`), показываем `toast.success("Профиль сохранён")` и, если `fromCart`, ведём на `/cart`.
- Если сохранение прочих полей вернёт ошибку — показывать **конкретное сообщение** (`error.message`), а не общее «Ошибка сохранения». В частности, для `23505` на `idx_profiles_phone_unique` — «Этот номер уже привязан к другому аккаунту».
- Кнопка **Сохранить** дизейблится, пока телефон в поле не валиден (если он непустой).

### 2. Новый компонент `src/components/PhoneVerifyDialog.tsx`
Маленькая обёртка над тем же UX, что в `PhoneAuthForm` (4-значный код + countdown + повторная отправка), но как `Dialog` для использования в Settings. Внутри использует `send-otp` и `link-phone-to-account`. Возвращает `onSuccess(phone)` после успешной привязки.

### 3. Никаких изменений в БД и edge-функциях не нужно
`link-phone-to-account` уже:
- проверяет код,
- проверяет, что телефон не занят другим `user_id` (возвращает 409 с понятным текстом),
- через service role обновляет `profiles.phone` и `phone_verified`.

`send-otp` уже работает (используется при регистрации/входе по телефону).

### 4. Что НЕ трогаю
- Auth, `verify-email-otp`, `send-email-otp` — там всё ок.
- RLS, схему БД, unique-индекс на телефоне (он правильный — один номер = один аккаунт).
- Прочие страницы.

## Технические детали

- `link-phone-to-account` требует `Authorization: Bearer <access_token>` — `supabase.functions.invoke` сам подставит его для залогиненного пользователя, дополнительных заголовков прокидывать не нужно.
- В Settings больше не отправляем `phone` обычным PATCH `profiles` от имени пользователя — это убирает конфликт с unique-индексом на клиенте и централизует привязку телефона через edge-функцию.
- Сообщения об ошибках от PATCH профиля парсим из `error.message` / `error.code` (для 23505 — отдельный человекочитаемый текст).

## Итог для пользователя

- Сохранение профиля перестанет молча «терять» телефон — будет понятное сообщение, если номер занят.
- Телефон в Settings теперь подтверждается кодом, как и при регистрации по телефону.
- После успешной привязки и заполнения имени/адреса вернёт обратно в корзину, и оформление заказа пройдёт.
