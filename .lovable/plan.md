План исправления логики времени доставки и самовывоза

Найденные проблемы

1. Нулевое время приготовления превращается в 90 минут
- В /checkout много мест используют `(prep_time_minutes || 90)`.
- Поэтому товар `d82788df-41cb-48d7-ab13-0c3556e093e5` с `prep_time_minutes = 0` считается как 90 минут готовки.
- Из-за этого продавец с окном с 09:00 получает готовность 10:30 вместо 09:00.

2. Для доставки выбран только один “bottleneck” продавец, а не все продавцы
- Сейчас `fastDeliveryResult` сначала ищет продавца с самой поздней готовностью, а потом передаёт в `calculateDeliveryTime` только его.
- Это опасно для корзины с несколькими продавцами: остальные графики/занятость/отпуск могут быть проигнорированы.

3. Расписание доставки “в указанное время” фактически даёт слишком свободный выбор
- Слоты доставки строятся только по общим настройкам доставки и `earliestMinutes`.
- На будущие даты после первой доступной даты слоты начинаются с `delivery_start_hour`, без проверки, что продавцы реально работают/могут подготовить заказ к этому времени.
- Также выбранная дата доставки блокируется только по общим busy/vacation датам, а не по реальной доступности всех продавцов в конкретный день.

4. Самовывоз строит слоты только целыми часами
- `getSellerTimeSlots` генерирует `09:00–10:00`, `10:00–11:00` и т.д.
- Если готовность 10:30, первый возможный слот 10:30–11:30 не появляется, и список начинается с 11:00.
- Поэтому при окне продавца с 09:00 покупатель может видеть выбор только с 11:00.

5. Нет минимального окна самовывоза 30 минут
- `calculatePickupTime` показывает диапазон `readyTime–slotEnd` без проверки минимальной длины.
- Поэтому для товара `263ae7ff-fbe1-45bd-a6da-e3566db16857`: 840 минут готовки, продавец работает 10:00–17:00, готовка переносится на второй рабочий день и заканчивается ровно в 17:00. UI показывает `28.04 17:00–17:00`.
- Правильно: если после готовности до конца окна меньше 30 минут, эту дату нельзя предлагать; нужно искать следующее рабочее окно и показывать минимум 30 минут, например `следующий рабочий день 10:00–10:30` или полноценный доступный диапазон.

6. Комментарии и реальная логика расходятся
- В `pickupUtils.ts` комментарий говорит про буфер 30 минут перед концом окна, но код специально убрал буфер: “No buffer”.
- Это создаёт путаницу и привело к ошибке `17:00–17:00`.

7. Лимит заказов по датам считается по `orders.created_at`, а не по дате выдачи
- RPC `get_orders_count_by_dates` считает заказы по дате создания заказа.
- Для ограничения “макс. заказов в день” нужно считать по дате, на которую запланирован самовывоз/готовность, иначе лимит будет работать неверно.
- Сейчас в базе нет нормального структурного поля для даты/времени самовывоза по каждому продавцу; есть только текст `estimated_delivery_time`, поэтому полноценное исправление лимитов лучше выделить как отдельный небольшой DB-этап.

Что будет сделано

1. Вынести всю математику в единый модуль
- Переписать `src/lib/pickupUtils.ts` так, чтобы там были отдельные функции:
  - нормализация времени приготовления: `0` остаётся `0`, fallback используется только если значения реально нет;
  - расчёт готовности продавца по графику с carryover;
  - расчёт первого доступного окна самовывоза с минимумом 30 минут;
  - генерация доступных слотов самовывоза с шагом 30 минут;
  - расчёт ближайшей доставки с учётом всех продавцов в корзине;
  - генерация слотов доставки с учётом реальной готовности заказа и рабочего окна доставки/пункта выдачи.

2. Ввести правило минимального окна самовывоза 30 минут
- Если товар готов в 17:00, а продавец закрывается в 17:00, этот день не показывается.
- Если товар готов в 16:45 при закрытии 17:00, этот день тоже не показывается.
- Минимально допустимый интервал выдачи: 30 минут.

3. Исправить нулевое время приготовления
- Во всех местах /checkout заменить `prep_time_minutes || 90` на безопасную функцию.
- Для `prep_time_minutes = 0` хлеб у продавца с графиком вторник/пятница с 09:00 будет доступен с 09:00, а не с 10:30.

4. Исправить слоты выбора времени самовывоза
- Генерировать слоты с шагом 30 минут, а не только целыми часами.
- На первой доступной дате начинать от фактической готовности, округлённой вверх до ближайших 30 минут, если нужно.
- Не показывать слоты, которые выходят за рабочее окно продавца или короче 30 минут.

5. Исправить доставку и пункт выдачи
- Для ближайшей доставки учитывать всех продавцов в корзине, а не только одного “узкого” продавца.
- Итоговое время доставки = самая поздняя готовность среди продавцов + среднее время доставки.
- Для пункта выдачи учитывать время закрытия выбранного пункта.
- Не показывать “любое время”, если заказ ещё физически не может быть приготовлен и доставлен.

6. Упростить `Checkout.tsx`
- Убрать локальные дублирующие расчёты `getSellerTimeSlots`, `isDateDisabledForSeller`, часть логики `availableTimeSlots`.
- Подключить централизованные функции из `pickupUtils.ts`.
- Так меньше риск, что карточка “ближайшая доставка”, календарь, селект времени и сохранённое `estimated_delivery_time` начнут считать по-разному.

7. Добавить тесты для критических сценариев
- Товар с `prep_time_minutes = 0`, график вторник/пятница 09:00–18:00: первый самовывоз с 09:00, не 10:30.
- Товар 840 минут, график 10:00–17:00: не показывать `17:00–17:00`, переносить на следующее доступное окно.
- Самовывоз: слоты с шагом 30 минут и минимумом 30 минут.
- Доставка: нельзя выбрать слот раньше готовности + времени доставки.
- Мультипродавец: итоговая доставка считается по самой поздней готовности среди всех продавцов.

Технические детали

- Основной файл: `src/lib/pickupUtils.ts`.
- Основной потребитель: `src/pages/Checkout.tsx`.
- Вспомогательно проверить `src/pages/Product.tsx`, `src/components/ProductCard.tsx`, `src/contexts/CartContext.tsx`, чтобы товар в корзине сохранял реальный `prep_time_minutes`.
- Базовое правило времени: все расчёты остаются в Минском часовом поясе, как указано в памяти проекта.
- БД на первом этапе менять не обязательно для исправления видимых ошибок. Но лимит “макс. заказов в день” сейчас концептуально считается по дате создания заказа; для идеальной точности после исправления UI нужно отдельной миграцией добавить структурные поля/таблицу для запланированных окон выдачи по продавцам.
